# 任务进展实时上报（progress）

## 为什么要有这个

之前 NPC 只在「心里」规划步骤，用户在 Issue / PR 里**看不到任何进展**，
只能盯着一条静止的评论干等，不知道是跑着还是卡了。

本能力把进展落成**一条可见的进度评论**，并随任务推进**原地刷新**：

```text
### 🚧 给 NPC 加进度上报
`▓▓▓▓▓░░░░░` 3/6 · 50% · 已耗时 18m20s

**🔄 正在做：接入文档**（已 6m10s）
> 正在写 SKILL.md

- ✅ 探测平台评论编辑能力 —— 用时 4m02s
- ✅ 实现进度脚本 —— 用时 8m08s
- 🔄 接入文档 —— 进行中，已 6m10s
- ⬜ 真实自测
- ⬜ 提交 PR

<sub>最后更新 2026-09-25 17:10:00（UTC+8） · 每 60s 自动原地刷新（心跳）</sub>
```

**进度要「详细」，不能只有计数。** 光给 `3/6 · 50%`，用户只知道还剩几步，
不知道 NPC 此刻在干什么、这一步是不是卡住了。所以务必：

1. **每开始一步就 `update --status running --note "在做什么"`** ——
   `note` 会显示在「🔄 正在做」区块里，这是用户看的第一行；
2. **别攒到做完才 update** —— 中间空转太久，用户看到的永远是上一次的旧状态；
3. **步骤措辞具体** —— 「查平台并发上限」远好于「调研」。

耗时（每步 `用时 4m02s`、进行中 `已 6m10s`、总计 `已耗时 18m20s`）由脚本自动算，
你只要老实按步骤打点即可。

## ⚠️ 打点纪律：先标 running，再干活，最后标 done

**开始时间只在标 `running` 那一刻记录。** 所以正确顺序是：

```bash
bash .cnb/scripts/npc-progress.sh update --step 2 --status running --note "在做什么"   # 开工就标
# ……干活……
bash .cnb/scripts/npc-progress.sh update --step 2 --status done                        # 做完再标
```

**跳过 `running`、直接标 `done` 的步骤没有真实耗时** —— 渲染成「未单独计时」，
正文脚注会写「是缺打点，不代表耗时 0s」。直接标 done 时脚本还会在日志里 warn 提醒你。

> 为什么较真：旧版在**任何** `update` 里都补开始时间，于是直接标 done 的步骤
> 算出 `started == done`，渲染成 **「用时 0s」** —— 看着像「这一步秒级完成」，
> 其实压根没打点。用户已在 Issue #12 就此提过问（「有的日志任务用时 0s？
> 而且这个任务并不简单」）。
>
> 秒级精度下真测出 0 会显示 **`<1s`**（量级），不写「0s」——「0s」会被读成「没花时间」。

**自查**：收尾前扫一眼 `preview`，出现「未单独计时」就说明你漏标了 `running`，
补打点也来得及（标一次 `running` 再标 `done`，耗时从补标那刻起算，
但至少不再是假数据）。

## 什么时候用

**默认就该用 —— 除了「一句话就能答完」之外的任何任务，开工第一件事就是 init。**

- 会跑命令 / 读文件 / 改代码 / 派子代理 / 多轮验证 —— 全部算
- 步骤 3~8 步，写成「查平台并发上限」这种**看得出在干什么**的措辞，
  不要写「调研」「处理」这类看不出内容的词
- 不确定要不要用？那就用。多一条进度评论的代价，远小于用户干等半天来问「你还在跑吗」

**不要用**：

- 纯问答 / 改一行文案 / 查个信息（秒回，纯属刷屏）

> 判断标准：**用户会不会盯着这个 Issue 等结果**。会等，就上进度。

> ⚠️ 实测教训：本仓 Issue #12 里 9 轮正式回复**只有 2 轮**带进度评论，
> 用户只能干等，最后专门来问「为什么好多都没有进度评论」。漏建比不建更糟 ——
> 用户会以为 NPC 没在干活。

## 用法

脚本：`.cnb/scripts/npc-progress.sh`

```bash
# 1) 开工：建立进度评论（步骤用 | 分隔）
bash .cnb/scripts/npc-progress.sh init \
  --title "给 NPC 加进度上报" \
  --steps "调研平台能力|实现脚本|接入文档|自测|提交 PR"

# 2) 推进：每开始 / 完成一步就更新（原地刷新同一条评论）
bash .cnb/scripts/npc-progress.sh update --step 1 --status done
bash .cnb/scripts/npc-progress.sh update --step 2 --status running --note "正在写 npc-progress.sh"
bash .cnb/scripts/npc-progress.sh update --step 2 --status done

# 3) 补充说明（追加到评论区底部的说明列表）
bash .cnb/scripts/npc-progress.sh note "发现平台并发上限 64，已加自动降级"

# 3b) 子代理台账（派了子代理时**由 subagent.sh 自动写**，一般不用手调）
#     一个子代理一行，按 SN 原地更新；收口后改状态、保留在清单里
bash .cnb/scripts/npc-progress.sh subagent --sn cnb-xxx --status running \
  --name 审查前端 --task "只读审查 src/web" --cpus 2 --thinking medium --limit 900

# 4) 收尾
bash .cnb/scripts/npc-progress.sh done --summary "已交付 PR #17"
bash .cnb/scripts/npc-progress.sh fail --reason "缺写权限，无法推送分支"
```

`--status` 取值：`pending` / `running` / `done` / `failed` / `skipped`
（`failed` 会把整条进度标为「已中止」；`done` 会把剩余步骤一并收尾）

子代理台账（`subagent`）：把「派了哪些子代理、各自什么状态」记进状态，
渲染成评论里一块**清单**（`🤖 子代理（共 N 个 · 进行中 X · 已收口 Y）`），
每个子代理一行 —— 状态、已耗时 / 上限、名字、任务摘要。按 `--sn` 原地更新，
**反复写只刷新那一行**，收口后保留在清单里便于追溯；耗时由渲染现算，
所以心跳每刷一次，在跑的那几行自己就往前走。
`--status` 取值：`pending` / `running` / `done` / `failed` / `timeout` /
`stopped` / `congested` / `unfinished`
（`timeout` 是「还在跑、父代理没等完」，`stopped` 才是被回收；收尾时仍在跑的会被
标成 `unfinished`，不谎报「已完成」）。

其它子命令：`show`（看当前状态）、
`link`（打印**那条进度评论**的定位链接 —— 收尾回复里附上它，方便用户回看）、
`preview`（只渲染成 Markdown 打到 stdout，**零写请求** —— 自测渲染改动时用它，
不用碰真实 Issue：评论发出去就删不掉）、
`list`（只读列出该 Issue / PR 上的进度评论，供维护者清理时参考）。

常用全局选项（放在子命令前）：`--repo`、`--issue`、`--pr`、`--state`、`--timeout`。

## 心跳：长步骤里评论「自己会动」

**你不需要做任何事，`init` 时已经自动开了。**

问题背景：NPC 一旦进到长步骤（读大文件、等子代理、跑测试、等 CI），就不会再调
`update`，评论整段静止。用户看到一条不动的评论，**分不清是「还在干活」还是
「早就断了」** —— 本仓 Issue #12 的反馈原话就是「这个评论的进度都没有动过呀」。

心跳解决它：`init` 会起一个**脱附的后台进程**，每 60s 原地 PATCH 同一条评论
（只刷新 `最后更新` / `已耗时`，**不新增评论**）。于是：

| 你看到的 | 含义 |
| --- | --- |
| 「最后更新」时刻在往前走 | 任务活着（哪怕步骤列表没变） |
| 「最后更新」很久不动 | 真卡住了 —— 对照构建日志查 |

```bash
# 一般不用手动调；需要时：
bash .cnb/scripts/npc-progress.sh heartbeat start    # 起（init 已自动起）
bash .cnb/scripts/npc-progress.sh heartbeat stop     # 停（done / fail 已自动停）
NPC_PROGRESS_HEARTBEAT=0 bash .cnb/scripts/npc-progress.sh init ...   # 关掉它
```

心跳由脚本自己看管，边界都堵好了：

- **收尾即停**：`done` / `fail` 会停掉它，状态一转 `done` 它也会自己退出；
- **只 PATCH 同一条**：绝不新增评论（append 模式下直接拒绝启动 —— 那会刷条数）；
- **绝不写状态文件**：只读状态、只刷评论，不会和你的 `update` 抢写；
- **DRY_RUN 下不启动**：自测「零写请求」的承诺覆盖它；
- **最长存活封顶**：万一收尾没跑到，它也会自己退出，不会永远刷下去。

> ⚠️ 心跳**只解决「看出还活着」**，不解决「看出在干什么」。
> 所以打点纪律照旧：**每开始一步就 `update --status running --note "…"`**，
> 别指望心跳替你汇报进展。

## 关键约束

1. **同一目标 + 同一角色只有一个状态文件**，默认落在 `/tmp/npc-progress/`。
   并发任务互不干扰（按角色名区分）。需要隔离时用 `--state` 指定。
2. **一个任务一条评论：新任务新建，历史一律不改**。
   `init` 会**新建**属于本轮任务的那条评论，每次 `update` 都是 PATCH **它自己那一条** ——
   任务内始终只有 1 条，Issue 不会被刷屏。
   ⚠️ **绝不去改写历史任务的进度评论**：那是上一轮任务的现场记录（做到哪、每步多久、
   什么结论），改了就是篡改记录。用户已在 Issue #12 明确要求过这一点。
   判据是 `task_id`（默认 `CNB_BUILD_ID` = 一次召唤）：
   同一个任务再 `init` 只刷新自己那条，换了任务一律新建；
   `update` / `note` / `done` / `fail` 还会用 `assert_task_owner` 校验归属，
   遇到「上一轮任务留下的状态文件」直接报错，不会把新进度写进旧评论。
   （想恢复旧的「合并成一条」行为：显式 `NPC_PROGRESS_REUSE=1`，非默认路径。）
3. **必须在同一会话内完成 init → update → done**。
   状态文件在流水线容器里，跨会话（换一次召唤）不共享；
   新会话请重新 `init`，不要沿用旧状态。
4. **失败要如实反映**：确实做不下去就 `fail --reason "..."`，
   不要留一条永远停在 50% 的进度评论。
5. **心跳不是「免打点」的理由**：它只让「最后更新」自己走，
   让用户知道评论是活的；做到哪一步、在干什么，仍然只有你的 `update` 能反映。
6. **步骤别写太细、也别太粗**：3~8 步为宜，但每步要**看得出在干什么**。
   用户看的是「做到哪了 + 此刻在做什么」，不是操作日志，也不是「调研 / 处理 / 收尾」
   这种看不出内容的词。
7. **完工回复里附进度评论链接**（`npc-progress.sh link`）——
   Issue 评论多了以后，用户很难翻回那条进度评论。
8. **别手动多刷**：不用为了「让用户看到更多」而反复 update ——
   降级路径只报里程碑，多余调用不会多出评论，纯属浪费轮次；
   需要「更详细」就把步骤拆具体 + 每步带 `--note`，而不是把同一步刷很多遍。

## 工作原理（了解即可）

平台限制：**NPC 身份发的评论不允许再次编辑**（PATCH 返回
`403 forbidden to edit NPC generated content`）。
而**流水线 OCI 身份**建的评论可以被 NPC token 原地编辑，所以：

| 阶段 | 做法 |
| --- | --- |
| `init` | 派一条**轻量子流水线**（OCI 身份）建评论，回传 `comment_id` |
| `update` | 主代理**直接 PATCH** 那条评论（零等待、零额外构建） |

**新任务新建、历史不改**（默认行为）：`init` 直接新建本任务的评论，
历史评论一个字节都不碰。判据是状态里的 `task_id`（默认 `CNB_BUILD_ID`）——
**同一个任务**再 `init` 只刷新自己那条（不重复建），**换了任务**一律新建。
于是每个任务在自己的评论里留一份完整记录，彼此不覆盖。

> 历史实现是「滚动复用一条」（把新任务写进旧评论）。这个策略已被**用户明确否掉**：
> 一个任务就要一条自己的过程评论。所以默认值反转为 `NPC_PROGRESS_REUSE=0`，
> 想做合并只能显式开 `NPC_PROGRESS_REUSE=1`（且只认已收尾、非 NPC 身份的历史评论）。

**自动降级**：子流水线起不来时（无触发器权限、跨仓受限、
**根组织并发构建超限**、超时、缺 cnb CLI 等），自动切到 **append 模式**——
追加一条评论。但**只报里程碑**：初始 + 进度每跨 25% 一档 + 收尾，
且非收尾播报最多 2 条。所以一个任务在 append 模式下**最多 3 条评论**，不会刷屏。
唯一例外是**改判**：某步 `failed` 后你又换方案跑完并 `done`，这次结论必须发出去 ——
否则 Issue 上最后留着的就是那条「❌ 已中止」，用户会以为整轮都挂了。
你在日志里会看到：

```text
npc-progress: 进度子流水线未成功（status=error）：...并发构建数量超出根组织限制：64
npc-progress: 改用「追加播报」模式（每次更新追加一条评论；内容相同时自动跳过）
```

**这不是故障**，进展照样可见，继续按原流程 update 即可，不用重试 init。

想强制降级路径做验证：`NPC_PROGRESS_MODE=append`；
小任务想干脆关掉：`NPC_PROGRESS_MODE=off`。

## 已知边界（踩过坑，别再踩）

- **同一 Issue 上同一角色被召唤两次**，会共用同一个状态文件（按 仓库+目标+角色 定位）。
  现在这**不会**改到旧评论：新任务的 `task_id` 与状态里记的不一致，
  `update` / `note` / `done` / `fail` 会直接报错，提示你先 `init`。
  并发跑多任务时用 `--state` 显式隔离，或换角色召唤。
- **历史评论默认一个都不碰**（`NPC_PROGRESS_REUSE=0`）：连上一轮没跑完的僵尸评论也留着。
  只有显式 `NPC_PROGRESS_REUSE=1` 才会去改写一条已收尾的历史评论；
  该路径下按 `role=` 归属判断，别的角色的进度评论不会被改写。
- **收尾只放行一次**（外加改判一次）：`done` / `fail` 的第一次播报无条件发出
  （用户必须看到结论），之后 `note` / 重复 `done` 都回到闸门内；但
  **`failed` 之后又 `done`** 属结论变更，也一定发得出去。
- **每步备注不随收尾消失**：`update --step N --status running --note "..."` 写的说明
  会一直留在那条评论上（标 done / 收尾都不清）。所以别用 `note` 传临时状态 ——
  它就是这一步的长期说明，要改就再传一次 `--note` 覆盖。
- **收尾标题如实**：`done` 时若还有 `failed` 步骤（它们会被原样保留），标题写
  「已完成 N/M 步（K 步失败）」，不会谎报「全部完成」。`skipped` 是主动决定，不降级。
- **退回排队（`pending`）会清掉该步计时**：它不再「进行中」，重新标 `running` 才重新起算。
- **状态文件损坏会直接报错**（不会发空评论）；恢复方式：删掉状态文件重新 `init`。
- **`--step` 不接受前导零**（`08` / `010` 会被当八进制），请写 `8` / `10`。

## 为什么「少发评论」是硬要求

平台**没有删除评论的 OpenAPI**（实测各种路由均 404），
而且**NPC 改不了自己发的评论**（403）。这意味着：**发出去的评论删不掉、也改不掉**，
多发的每一条都会永久留在 Issue 里。所以本能力的原则是——

- 正常路径：**一个任务一条**，任务内全程只 PATCH 自己那一条；
- 降级路径：也**封顶**，只报里程碑；
- 自测时用 `NPC_PROGRESS_DRY_RUN=1`：只渲染、不发任何写请求，**零残留**。

而「删不掉」**不是**拿旧评论顶替新任务的理由 —— 历史是记录，不能篡改。

维护者想清理历史残留评论：`bash .cnb/scripts/npc-progress.sh list` 先看清有哪些，
再在网页端手动删（NPC 无删除权限）。
