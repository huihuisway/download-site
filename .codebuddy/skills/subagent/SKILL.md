# 子代理（Subagent）

把一个**独立、可并行、上下文需要隔离**的子任务派发给「子代理」，
由它在**独立的 npc:go 会话**里执行，父代理拿到文本结论后汇总。

> ⚙️ **前提：主容器是 4 核 8G 的主力，不是只会派活的调度器。**
> 读文件 / grep / 发评论 / 改几处代码 / 小脚本**自己直接干** ——
> 派一条子代理要付「起流水线 + 等 + 取回」的固定开销，比两三步的小活还贵。
> 真正值得外派的是三种：**吃 CPU**（编译 / 跑测试 / 压测）、
> **吃内存**（大批量转码）、**值得并行**（多个互不依赖的子任务）。
> 主容器规格**启动即固化**，运行中改不了，所以重活只能在**派发时**给规格。

## 什么时候用

适合派子代理：

- 任务可拆成互不依赖的几块（如同时调研 3 个方案、分别审查 3 个目录）
- 子任务会产出大量中间过程（读一堆文件、翻日志），不想污染主上下文
- 子任务需要独立运行环境 / 独立超时（跑测试、跑构建、跑长命令）
- 需要同一件事的多个独立视角（并行出多份结论再对比）
- **复杂任务**：主线被流水线运行时长卡着时，把能并行的部分外派，
  用墙钟时间换总时长（子代理各跑各的，不叠加主代理的时长）
  —— 但**先量一下还剩多少**：`bash .cnb/scripts/npc-budget.sh`，
  `结论=wrapup`（≥70%）时先落盘 + 回帖，别再派对新的子代理

不要派子代理：

- 子任务依赖主线的对话上下文（子代理看不到，必须把上下文写进 `--task`）
- 只有一两个文件的小改动，直接做更快
- 需要多轮来回确认的任务（子代理是一次性的，中途无法交互）

## 并发上限：根组织级 64 条（实测）

平台对**根组织**限制「同时运行的构建数 / 流水线数」**各 64 条**。
超出时**不排队**：构建照常创建、短暂显示 `pending`，随后 1~20 秒内被判 `error`：

```text
The number of concurrent builds has exceeded the limit set for the root organization: 64.
并发构建数量超出根组织限制：64
```

要点：

- 这 64 条是**整个根组织**共享的额度，主代理自己、PR 构建、定时任务都占额度；
- 判据是**失败原因**，不是「拿到 sn」—— 拿到 sn 只代表请求被受理；
- 别用「并发越多越快」的思路硬冲：超限后那些子任务**白建一场**（计构建记录、不计 token）。

脚本已内置对策，正常用法下**不需要你手工控并发**：

| 场景 | 行为 |
| --- | --- |
| `run`（同步） | 触发后做「准入确认」，撞上限就等位补投，最多 `--retry` 次（默认 30） |
| `run --async` | 同上；等位耗尽时退出码 `3`（可重试，不是真失败） |
| `map` | 并发闸门 + 撞上限放回队列重投，最稳 |
| `wait` | 撞上限退出码 `2`，与真失败（`1`）分开 |

## 用法

脚本：`.cnb/scripts/subagent.sh`

```bash
# 同步：派出子代理并等它跑完，stdout 就是它的结论
bash .cnb/scripts/subagent.sh run \
  --name 依赖调研 \
  --task "读取 package.json 与 pnpm-lock.yaml，列出所有运行时依赖及其用途，每条一行。" \
  --thinking off \
  --timeout 600

# 常驻参数
#   --name            子代理名字（日志里便于区分，同时发给对方作为身份）
#   --system          自定义系统提示（默认已内置「只汇报结论」约束）
#   --model           模型 ID，默认 deepseek-v4.1-flash
#   --thinking        思考档位，支持 auto（推荐）或 off/minimal/low/medium/high/xhigh/max
#   --cpus            规格核数，支持 auto（推荐）或 1~64，默认 2
#   --timeout         等待上限（秒），默认 1800
#   --max-chars       回显给父代理的字符上限，默认 12000，0 为不截断
#   --out             把完整结论落盘到文件（结论长时必用，再分段读）
#   --write           授予子代理代码写权限（默认只读）
#   --retry           撞并发上限时的补投次数，默认 30
#   --congestion-wait 每次补投前等待秒数，默认 15
```

### 两个 auto：规格与思考档都别自己拍

`--cpus auto` 与 `--thinking auto` 都按**任务文本里的信号**定档，依据打 stderr 可核对：

```bash
bash .cnb/scripts/subagent.sh run --cpus auto --thinking auto \
  --task "跑一遍 pytest 全量单测并汇总失败用例"
# stderr: subagent[think]: 命中信号「复杂实现（重构、多文件改动、调试报错）」→ high
# stderr: subagent[spec]: 命中信号「有真实计算段（跑测试 / 打包 / 静态检查）」→ 4 核
（这两行是**实跑输出**；档位按信号取最高档，所以「跑测试」这种带计算段的任务
会落到 high 而不是 medium —— 示例与代码不一致会让人以为 auto 判错了）
```

| 信号 | `--cpus` | `--thinking` |
| --- | --- | --- |
| 等模型返回 | 2 核 | —— |
| 有真实计算段 | 4 核 | —— |
| CPU 密集 / 吃内存 | 8 核 | —— |
| 纯搬运（改文案） | —— | `off` |
| 读与查 | —— | `low` |
| 常规实现 | —— | `medium` |
| 复杂实现（重构 / 调试） | —— | `high` |
| 疑难（架构 / 根因） | —— | `max` |

规格不够会**自主升档重投**（`--escalate`，只认 OOM 硬证据）；`map` 里两条都**逐条判**，
所以一张清单上「改文案」和「根因排查」混着也能各取所需。

### 回收：别让子代理白占额度

留在场上会继续占**根组织 64 条并发额度**，并按**声明规格**继续烧核时：

```bash
bash .cnb/scripts/subagent.sh stop --sn <构建号>   # 停掉仍在跑的子代理
```

- 升档重投前脚本会**自动回收**旧的（超时那条路径上它可能还活着）；
- 重投次数用尽时**不自动回收** —— 你可能还想 `status --sn` 查它，静默停掉等于毁现场。

## 批量：map（推荐用于 3 个以上子任务）

任务清单每行一个子任务，`名字<TAB>描述` 或整行当描述：

```bash
cat > /tmp/tasks.txt <<'TASKS'
# 空行和 # 开头的行会被忽略
前端审查	src/web 目录只读审查，列 Top3 风险点，每条一行。
后端审查	src/api 目录只读审查，列 Top3 风险点，每条一行。
依赖盘点	读取 package.json，列运行时依赖及用途，每条一行。
TASKS

bash .cnb/scripts/subagent.sh map --file /tmp/tasks.txt \
  --concurrency 8 --thinking low --timeout 900 --out-dir /tmp/sub-results
```

- `--concurrency`（默认 8）：同时最多几个在场，**不会撞 64 上限**（还留了余量给主代理与 PR 构建）；
- 谁先结束就补投下一个，不用等满一批；
- 撞上限的任务**放回队列**稍后重投（上限 `--retry` 轮），不会丢；
- `--out-dir` 把每份结论落盘成 `<名字>.md`，失败落 `<名字>.error.txt`；
- stdout 最后给出按清单顺序的**结论汇总**与「成功/失败/超限」统计。

手写并行循环也可以，但要自己控制在场数量：

```bash
SNS=""
for mod in api web cli; do
  sn=$(bash .cnb/scripts/subagent.sh run --async \
        --name "review-$mod" --thinking off --timeout 900 \
        --task "只读审查 src/$mod 目录，列出 Top3 风险点，每条一行。" 2>/dev/null)
  SNS="$SNS $sn"
done

for sn in $SNS; do
  bash .cnb/scripts/subagent.sh wait --sn "$sn" --timeout 900 --max-chars 4000
done
```

## 退出码

| 码 | 含义 | 处理 |
| --- | --- | --- |
| `0` | 成功（stdout 为结论） | 直接用 |
| `1` | 真失败（构建报错；配置 / 权限类错误也算这类） | 看自动回显的失败 Stage 尾部日志 |
| `2` | 并发超限，没跑起来（`wait` / 同步 `run` / `map` 都复用该码） | 可重试；减少并发或稍后重投，别当失败丢弃 |
| `3` | `run --async`：并发超限，等位耗尽 | 同上 |
| `124` | 等待超时，子代理仍在跑（`map` 到达总时长上限也返回它） | 用 `status --sn` 继续查，确认不等了就 `stop --sn` 回收 |

> ⚠️ 历史坑：`run` 曾经把**配置类错误**（如 event 未授权）也报成「并发已达 64」、
> 返回可重试的 `3`，于是 `map` 会白等 30 轮 × 15s。现已分开：容量问题才返回 2/3，
> 配置类错误直接返回 `1`。

## 父子之间到底通了多少信息（实测量过，别想当然）

四条链路，2026-10-01 在本仓逐条实测：

| 方向 | 现状 | 说明 |
| --- | --- | --- |
| 父 → 子 | ✅ 自动注入 | env 里带 `SUBAGENT_PARENT_SN` / `SUBAGENT_PARENT_TARGET_TYPE` / `..._TARGET_NUMBER` / `..._TARGET_URL` / `..._PROGRESS_URL`；system prompt 里另有一段「你的出处」给模型看 |
| 等待期 | ✅ 有心跳 + 台账 | 每 `SUBAGENT_HEARTBEAT_INTERVAL`（默认 60s）打一行「仍在等待…」，同时把父进度评论里的**子代理台账**刷一次（一个子代理一行，按 SN 原地更新） |
| 子 → 父 | ✅ 带出处 | 结论走 stdout，出处（SN / 日志链接 / 规格 / 思考档）走 stderr，并写进 `--out` 落盘文件的开头 |
| 失败 / 超时 | ✅ 抢救部分结论 | 从 AI 请求明细里捞出它中止前已产出的正文，标注「不完整，仅供抢救参考」 |

**为什么要注入父上下文**：实测子代理容器里 `env | sort` 只有
`SUBAGENT_NAME` / `TASK` / `SYSTEM` / `MODEL` / `THINKING` / `CPUS` / `MAX_BYTES` / `DEPTH`
八个变量 —— **没有**父 SN、没有 Issue/PR 编号、没有父进度评论链接。
子代理不知道自己从哪儿被派出来的，结论回来也引不出来源。

**为什么等待期要有心跳**：等子代理期间父代理如果零输出，会被 `npc:go` 的
「无输出超时」掐掉（本仓实测有过一次 `map` 调用在 **10 分 0 秒**被强制关闭）；
用户那边同样看不出「在跑」还是「卡死」。

**为什么失败要抢救**：子代理被中止 / 超时时，它**已经产出的正文**照样烂在
AI 请求明细里，旧版父代理只收到一句「未成功」。真机：一次 10 路子代理并行审计，
10 路全在 ~9 分钟处被平台中止，产出一个字都没拿回来。

> 抢救出来的内容**不是**完整结论，会在输出里明确标注；要完整结论仍需重跑子任务。

### 等待期在 Issue 里长什么样（子代理台账）

父进度评论里会渲染出一块**清单**，每个子代理一行 —— 状态、已耗时 / 上限、名字、任务摘要：

```text
**🤖 子代理（共 3 个 · 进行中 1 · 已收口 2）**

- 🔄 `cnb-4gs-1k47ff5gr` 「审查前端」已 16m01s / 上限 40m00s · 运行中 · 2 核 · 思考 medium — 只读审查 src/web，列 Top3 风险点
- ✅ `cnb-4gs-1k47ff5ga` 「审查后端」用时 9m00s · 已完成 · 4 核 · 思考 high — 只读审查 src/api，列 Top3 风险点
- ❌ `cnb-4gs-1k47ff5gb` 「跑测试」用时 5m00s · 失败 — 跑一遍全量单测
```

为什么不是「一条心跳追加一行」：旧写法会把「仍在等待子代理 X（已 900s / 上限 2400s，
状态 pending）」刷成 19 条，同一件事重复十几遍。现在是**按 SN 一行**：
反复刷只更新那一行，收口后改成「已完成」并**保留在清单里**（历史可追溯）。
耗时由渲染现算，所以评论心跳每刷一次，在跑的那几行自己就往前走一格。

| 台账状态 | 什么时候标 |
| --- | --- |
| `running` / `pending` | 派出后；等待期心跳按构建状态刷新 |
| `done` | 取回结论成功（`cmd_wait` / `reap_result` 两条收口路径） |
| `failed` | 构建失败，或构建成功但结论取回失败 |
| `timeout` | 等待超时 —— 子代理**仍在跑**（要停就 `stop --sn`，那会标 `stopped`） |
| `congested` | 并发超限，压根没开跑（可重试） |
| `stopped` | 被回收（`stop --sn` / 升档重投前的回收） |
| `unfinished` | 父任务收尾时它还没等到（不谎报「已完成」） |

写入走 `npc-progress.sh subagent --sn <sn> --status <状态> [--name/--task/--cpus/
--thinking/--limit]`；父代理没建进度评论时全程静默跳过（不会为一次派发凭空建评论）。

开关：`SUBAGENT_HEARTBEAT_INTERVAL`（心跳间隔）、`SUBAGENT_PROGRESS_INTERVAL`
（台账刷新的限流间隔，默认 60s；**终态不受限流** —— 收口那一笔必须落到清单上）、
`SUBAGENT_PROGRESS_SCRIPT`（进度脚本路径）、`SUBAGENT_TASK_DIGEST_CHARS`
（台账里任务摘要的字符数上限，默认 80）。

## 结果与限制

- stdout 即子代理结论，可直接汇总进主回复；结论长时用 `--out` 落盘后再读。
- 子代理是**一次性的**：它拿不到主线的对话上下文（但**拿得到**父 SN / 父任务链接，
  见上一节），也不会追问，`--task` 仍然必须自包含。
- 子代理跑在**独立流水线**里，会单独计入构建记录与用量；别用来做琐碎小事。
- 反过来，**重活也别硬扛**：主容器 4 核 8G 装得下大多数活，但编译 / 压测很吃 CPU ——
  留在本地会拖慢自己，也占着主流水线的时长预算（外派等于把耗时挪到另一条流水线）。
- **别一概外派**：只有一两个文件的小改动、读几个文件问个问题，本地做更快。
- 数量：并发闸门默认 8 已足够；**单次任务总数建议 ≤ 20**（受根组织 64 条额度与 AI Credits 约束），
  超过就分批，别一次全推上去。
- 单个子代理**同样受流水线运行时长上限约束**，别派超长任务；`--timeout` 只是父代理的等待上限。
- 子代理默认**只读**；确需改代码时才加 `--write`，并让多个写型子代理落在互不重叠的文件上。
- **禁止无限套娃**：脚本按 `SUBAGENT_DEPTH` 计数，超过 `SUBAGENT_MAX_DEPTH`（默认 2）
  会直接拒绝派发。到上限时请自己完成子任务。

## 排查

- `subagent: 触发子代理被拒绝` → `CNB_TOKEN` 无触发构建权限，或事件名被改坏。
- 一直 `pending` → 正常，构建在跑；等即可。
- `并发构建数量超出根组织限制：64` → 不是配置错误，是容量问题：少派一些、稍后重试，
  或用 `map` 的 `--concurrency` 让脚本自己排队。
- `status=error` → 脚本已自动回显失败 Stage 的尾部日志，按日志定位。
